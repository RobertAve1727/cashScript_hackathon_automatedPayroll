# BCMR — making ePHP and the Employment NFT render as names, not hashes

Backlog task **T27**. A [Bitcoin Cash Metadata Registry][chip] entry so that a wallet showing an
eSahod payroll transaction says *"eSahod Peso"* and *"eSahod Employment"* instead of
`0f1e2d3c4b5a…`. Paytaca runs [`bcmr-indexer`][indexer], so a correctly published registry shows
up in-wallet without asking anyone's permission.

**Read the honesty section at the bottom before you trust any of this.** Nothing here has been
published to a live chain. What *has* been machine-checked is listed there precisely.

| File | What it is |
|---|---|
| [`registry.json`](registry.json) | The registry **template**. Valid BCMR v2, but the category IDs and the hostname are placeholders. Committed. |
| `registry.published.json` | Generated by the publish script. The exact bytes you host, with real category IDs substituted in. Commit it or don't — it is reproducible from `registry.json` + `deployment.json`. |
| [`../scripts/esahod/05-publish-bcmr.ts`](../scripts/esahod/05-publish-bcmr.ts) | Substitutes, hashes, and prints the OP_RETURN. **Broadcasts nothing.** |

---

## 1. What is in the registry

Two identities, because eSahod mints two categories:

**`EPHP` — the payroll unit.** A plain fungible CashToken, `decimals: 2`, so a raw amount of
`3500000` displays as `35000.00`. One unit is one centavo, which is the same unit the statutory
engine and the covenant use everywhere; there is no conversion anywhere in the system.

**`ESAHOD-EMP` — the employment record.** A mutable NFT per employee whose 40-byte commitment
*is* the employment contract. It is described as a **parsable NFT collection**: the registry
carries VM bytecode that a client runs to split the commitment into eight named, typed fields.

### The parse bytecode

```
00cf8292766b6301147f7c6b547f7c816b547f7c816b547f7c816b527f7c816b527f7c816b517f7c6b816b677568
```

```
OP_0 OP_UTXOTOKENCOMMITMENT      push the NFT's commitment
OP_SIZE OP_0NOTEQUAL             1 if it has any bytes, 0 if it is the empty minting baton
OP_DUP OP_TOALTSTACK             ← altstack bottom = the NFT type id
OP_IF
  <20> OP_SPLIT OP_SWAP           OP_TOALTSTACK   payeePkh   (raw 20 bytes, `hex`)
  OP_4 OP_SPLIT OP_SWAP OP_BIN2NUM OP_TOALTSTACK  monthlyBasic
  OP_4 OP_SPLIT OP_SWAP OP_BIN2NUM OP_TOALTSTACK  monthlyAllowance
  OP_4 OP_SPLIT OP_SWAP OP_BIN2NUM OP_TOALTSTACK  taxPerPeriod
  OP_2 OP_SPLIT OP_SWAP OP_BIN2NUM OP_TOALTSTACK  nextPeriod
  OP_2 OP_SPLIT OP_SWAP OP_BIN2NUM OP_TOALTSTACK  endPeriod
  OP_1 OP_SPLIT OP_SWAP           OP_TOALTSTACK   status     (raw 1 byte, `boolean`)
                        OP_BIN2NUM OP_TOALTSTACK  employeeNo (the trailing 3 bytes)
OP_ELSE
  OP_DROP
OP_ENDIF
```

Three decisions in there are worth naming, because they are not obvious:

- **`OP_BIN2NUM` on every numeric field.** A BCMR `number` field is read as a VM number, and VM
  numbers are minimally encoded. `monthlyBasic` for ₱35,000.00 is `e0673500` in the commitment —
  four bytes with a zero high byte, which is *not* minimal. A client decoding that with a strict
  reader (libauth's `vmNumberToBigInt` requires minimal encoding by default) would report an
  error instead of `3500000`. `OP_BIN2NUM` normalises it on the way to the altstack. Most
  Philippine salaries land in exactly this range, so this is the common case, not an edge case.
- **No `OP_BIN2NUM` on `status`.** The spec renders a `boolean` field as `true` only for exactly
  `0x01` and `false` only for exactly `0x00`; `OP_BIN2NUM` would turn `0x00` into the empty
  string and break it. *Failure mode to be aware of:* if a commitment ever held a status byte
  other than `0x00`/`0x01`, a spec-following client must treat **the whole NFT** as unparsable.
  That cannot happen here — `encodeCommitment` rejects any other value and the minting baton is
  burned during enrolment — but if you would rather not rely on that, change the `status` field's
  encoding to `{"type": "number"}` and delete nothing else. The bytecode already produces the
  right bytes for both.
- **The type id is a flag, not a byte from the commitment.** The layout uses all 40 bytes, so
  there is no room for a discriminator. `OP_SIZE OP_0NOTEQUAL` gives `01` for a 40-byte
  employment record and `` (empty) for the zero-length minting baton, which become the two keys
  in `parse.types`.

### Schema decisions you should sanity-check

- **The symbol is `EPHP`, not `ePHP`.** BCMR requires `/^[-A-Z0-9]+$/` for `token.symbol`. The
  lowercase `e` is illegal, so `ePHP` lives in the identity `name` and `description` instead.
  Note the JSON Schema does not itself carry that `pattern`, so `ePHP` would *validate* — it
  would just be violating the written spec, and validators that check the regex separately would
  reject it. Change it if you disagree; it is one string in two places.
- **`unit` on the money fields is `PHP`, not `EPHP`.** They are contractual peso figures that
  happen to be disbursed 1:1 in ePHP units. `"35000.00 PHP"` is what a payroll officer expects.
- **`defaultChain` is chipnet** — `00000000040ba9641ba98a37b2e5ceead38e4e2930ac8f145c8094f94c708727`,
  the value the spec names for chipnet. Change it for mainnet.
- **The file is pure ASCII on purpose.** Paytaca's indexer hashes `response.text`, i.e. the file
  *after* a decode/re-encode round trip through Python. If your host omits `charset=utf-8`,
  `requests` guesses the encoding, and a guess that differs from UTF-8 changes the bytes and
  therefore the hash. ASCII cannot be guessed wrong. `05-publish-bcmr.ts` warns if you introduce
  a non-ASCII byte.

## 2. The part that will bite you: the authchain

BCMR does not key metadata by category. It keys it by **authbase**, and it only reads the
metadata published in the **authhead** — the transaction at the tip of the chain of
output-0-spends starting from the authbase. From the CHIP:

> Once the registry's authhead transaction has been acquired and validated, the client must
> inspect the authhead transaction's outputs to locate the metadata registry publication output.

For a CashToken, the authbase is the transaction whose txid equals the category ID. Per the
CashTokens spec, that is the **parent** transaction whose output `0` the genesis transaction
spent:

> only token genesis inputs – inputs which spend output `0` of their parent transaction – are
> eligible (i.e. outpoint transaction hashes of inputs with an outpoint index of `0`).

So for eSahod the chain is:

```
faucet/funding tx   (txid == the category ID)   ← authbase, identity output = its vout 0
      └─ spent by 01-deploy.ts's genesis tx     ← its OWN vout 0 is the next identity output
            └─ … whoever spends that vout 0 …   ← authhead moves every time
```

### `01-deploy.ts` as written puts the identity output somewhere you cannot use

For ePHP, output 0 of the genesis transaction is the ePHP supply sent to the `PayrollTreasury`
token address. The moment the first payroll runs, that output is spent by `paySalary`, whose
output 0 is **the employee's net pay** — so the ePHP authhead walks off into an employee's
wallet and your metadata stops resolving. For the employment category, output 0 is the minting
baton to HR, which `02-enrol-employees.ts` spends into the vault; same problem one step later.

The fix is two lines per genesis transaction: reserve output 0 as a dust output the keeper
controls, and move the token to output 1. In [`../scripts/esahod/01-deploy.ts`](../scripts/esahod/01-deploy.ts):

```ts
const mintEphp = new TransactionBuilder({ provider });
mintEphp.addInput(ephpInput, keeper.unlockP2PKH());
mintEphp.addOutput({ to: keeperAddress, amount: GENESIS_DUST_SATOSHIS });   // ← ADD: identity output
mintEphp.addOutput({
  to: deployment.treasury.tokenAddress,
  amount: GENESIS_DUST_SATOSHIS,
  token: { amount: EPHP_TOTAL_UNITS, category: pesoCategory },
});
mintEphp.addBchChangeOutputIfNeeded({ to: keeperAddress, feeRate: 1 });
```

and the same insertion before the `mintEmployment` token output. Nothing downstream reads the
genesis transaction by output index — `02-enrol-employees.ts` finds the baton by scanning HR's
address for a minting UTXO of the right category, and `03-run-payroll.ts` finds ePHP at the
treasury address — so this is safe. **This change has not been made.** It is not in this task's
scope to alter a deploy script nobody has yet run against chipnet, but without it steps 4 and 5
below have nowhere to attach.

> **Separately:** `01-deploy.ts` picks its genesis inputs with `spendable.slice(0, 1)` and
> `spendable.filter(...)`, and never checks `utxo.vout === 0`. Only an input spending outpoint
> index `0` creates a category, and `pesoCategory = ephpInput.txid` is only the resulting
> category ID if that input's `vout` is `0`. If it is not, the genesis transaction mints nothing
> and every category ID in `deployment.json` — including the two this registry keys itself
> by — is wrong. Worth a `spendable.filter((utxo) => utxo.vout === 0)` before this is ever run
> for real.

## 3. Fill in the real category IDs and hash the file

After `01-deploy.ts` has written `scripts/esahod/deployment.json`:

```bash
npx tsx scripts/esahod/05-publish-bcmr.ts --host payroll.example.ph
```

Replace `payroll.example.ph` with the domain that will actually serve the file. The script:

1. reads `pesoCategory` and `employmentCategory` from `scripts/esahod/deployment.json`, refusing
   anything that is not 64 lowercase hex characters;
2. substitutes them for `REPLACE_WITH_PESO_CATEGORY_FROM_DEPLOYMENT_JSON` and
   `REPLACE_WITH_EMPLOYMENT_CATEGORY_FROM_DEPLOYMENT_JSON`, and `--host` for the
   `esahod.example` placeholder in every URI;
3. refuses to continue if any `REPLACE_WITH_` survives, or if the result is not JSON whose
   `identities` map is keyed by both real categories;
4. writes `bcmr/registry.published.json`;
5. prints the SHA-256 of those exact bytes and the OP_RETURN locking bytecode.

Output looks like this (with a fabricated deployment):

```
template:  bcmr/registry.json
published: bcmr/registry.published.json  (9771 bytes)
  ePHP category:       0f1e2d3c4b5a69788796a5b4c3d2e1f00112233445566778899aabbccddeeff0
  employment category: b1a4e0d5c2f3968a7b0c1d2e3f405162738495a6b7c8d9e0f1a2b3c4d5e6f708

sha256 of those exact bytes (OP_SHA256 byte order, no reversal):
  05959993e7dc8e31a0580f79a10fe14fbcafa8e99f777f113253fa433c333121

OP_RETURN publication output:
  lockingBytecode: 6a0442434d522005959993…12706179726f6c6c2e6578616d706c652e7068
  size:            58 bytes (relay limit is 223)
  pushes:          OP_RETURN <'BCMR'> <hash> <uri>
    uri "payroll.example.ph" (18 bytes) -> https://payroll.example.ph/.well-known/bitcoin-cash-metadata-registry.json
```

Confirm the hash independently — it is the one number that must be exactly right:

```bash
shasum -a 256 bcmr/registry.published.json
```

`OP_SHA256` byte order is just the digest as every SHA-256 library emits it. **Do not reverse
it.** (It is the *opposite* of the byte order block explorers use for txids, which is why the
CHIP bothers to say so.)

### Other flags

```bash
# push a full URL instead of the bare domain — do this if your host will not serve a .well-known
# directory (GitHub Pages needs a .nojekyll file before it serves dot-prefixed paths at all)
npx tsx scripts/esahod/05-publish-bcmr.ts \
  --host esahod.github.io \
  --uri https://esahod.github.io/payroll/registry.json

# add an IPFS mirror as a second URI
npx tsx scripts/esahod/05-publish-bcmr.ts --host payroll.example.ph --uri ipfs://bafy…
```

The bare-domain form is the CHIP's canonical shorthand and Paytaca implements it
(`decode_url` prepends `https://`; `process_op_return` appends the well-known path when the
parsed URL has an empty path). Note that Paytaca's `process_op_return` reads the URI at a fixed
position — `op_return.split(' ')[3]` — so **push at least one URI**, and put the one you most
want fetched first.

## 4. Host the file

The bytes served must be byte-identical to what you hashed.

```bash
# example: any static host, at the well-known path
scp bcmr/registry.published.json \
    web@payroll.example.ph:/var/www/payroll/.well-known/bitcoin-cash-metadata-registry.json
```

Serve it as `application/json; charset=utf-8`, and make sure nothing in front of it
pretty-prints, minifies, or re-encodes. Then check what the world actually sees:

```bash
curl -sS https://payroll.example.ph/.well-known/bitcoin-cash-metadata-registry.json | shasum -a 256
# must equal the hash printed in step 3
```

## 5. Publish on chain — twice

One registry file covers both categories, but each category has its own authchain, so the same
OP_RETURN output has to appear in the authhead of **both**. That is two transactions.

Find each authhead:

```bash
CAT=0f1e2d3c…   # the ePHP category, then repeat for the employment category
curl -s "https://bcmr-chipnet.paytaca.com/api/authchain/$CAT/head/"
```

(If the indexer has not seen the category yet, the authhead is simply the genesis transaction —
its output 0 is unspent, which is the definition.)

Then, for each category, spend that authhead's output 0, put a fresh spendable output 0 back,
and carry the OP_RETURN:

```ts
import { binToHex } from '@bitauth/libauth';
import { ElectrumNetworkProvider, Network, SignatureTemplate, TransactionBuilder } from 'cashscript';

const AUTHHEAD_TXID = '…';                                   // from the curl above
const HASH = '05959993…';                                    // from step 3
const URI = 'payroll.example.ph';                            // from step 3

const keeper = new SignatureTemplate(process.env.ESAHOD_KEEPER_WIF!);
const keeperLock = binToHex(keeper.unlockP2PKH().generateLockingBytecode());
const provider = new ElectrumNetworkProvider(Network.CHIPNET);

const identityUtxo = (await provider.getUtxosForLockingBytecode(keeperLock))
  .find((utxo) => utxo.txid === AUTHHEAD_TXID && utxo.vout === 0);
if (identityUtxo === undefined) throw new Error('the authhead identity output is not spendable by the keeper');

const builder = new TransactionBuilder({ provider });
builder.addInput(identityUtxo, keeper.unlockP2PKH());
builder.addOutput({ to: keeperLock, amount: 1000n });        // output 0 — the NEW identity output
builder.addOpReturnOutput(['BCMR', `0x${HASH}`, URI]);       // output 1 — the publication output
builder.addBchChangeOutputIfNeeded({ to: keeperLock, feeRate: 1 });
console.log(await builder.send());
```

`addOpReturnOutput(['BCMR', '0x<hash>', '<uri>'])` produces byte-for-byte the locking bytecode
`05-publish-bcmr.ts` prints — verified against CashScript's own encoder. The `'0x'` prefix is
what tells CashScript to treat the hash as hex rather than as 64 ASCII characters; drop it and
you will publish a 64-byte push that no client will match.

Keep the output order. Output 0 must be spendable and yours: it is the identity output your
*next* metadata update will spend. Never make output 0 the OP_RETURN — BCMR reads a data-carrier
output at index 0 as "this identity is burned".

## 6. Verify the indexer accepted it

```bash
CAT=0f1e2d3c…

# did it find and validate the registry?
curl -s "https://bcmr-chipnet.paytaca.com/api/registries/$CAT/latest/"
```

Look at `validity_checks`. The indexer sets four flags, and all four should be true:

| Flag | False means |
|---|---|
| `bcmr_file_accessible` | it could not download your URI (HTTP status, TLS, or the well-known path is not served) |
| `bcmr_hash_match` | the bytes it downloaded do not hash to the value in your OP_RETURN |
| `bcmr_format_valid` | the JSON failed schema validation |
| `identities_match` | your `identities` map has no key equal to the authbase that published it — the wrong category, or the OP_RETURN went into the wrong authchain |

Then the wallet-facing views:

```bash
curl -s "https://bcmr-chipnet.paytaca.com/api/tokens/$CAT"
curl -s "https://bcmr-chipnet.paytaca.com/api/tokens/$CAT/icon-symbol"
curl -s "https://bcmr-chipnet.paytaca.com/api/registry/$CAT/identity-snapshot/token-category/nfts/parse/bytecode/"
curl -s "https://bcmr-chipnet.paytaca.com/api/bcmr/$CAT/reindex/"   # force a re-fetch after fixing the hosted file
```

Mainnet is the same API at `https://bcmr.paytaca.com`.

## 7. Updating the registry later

Metadata is not immutable, and updating it does not require a new category:

1. add a new timestamp key to the identity's history in `registry.json` (keep the old snapshot —
   that history is the point of the format), and bump `latestRevision` and `version.minor`;
2. re-run `05-publish-bcmr.ts` for a new hash;
3. replace the hosted file;
4. spend the *current* identity output (which is output 0 of the transaction you published in
   step 5) with a new publication transaction of the same shape.

Because the whole history is on chain, a wallet can show a user "this token was renamed" rather
than silently swapping a label.

## 8. Honesty

**Nothing in this directory has been published to any chain, and no wallet has ever rendered
it.** The chipnet deploy scripts themselves have never been run against a funded key
(see the README's "The chipnet path" section), so this sits one step further out than that.

Machine-checked, on this machine:

- `registry.json` and a substituted `registry.published.json` both **validate** against the
  official `bcmr-v2.schema.json` (draft-07) using `ajv-cli`.
- The `parse.bytecode` was executed as the CHIP's "standardized NFT parsing transaction" against
  the **real BCH VM** via libauth — under BCH2023, BCH2025 and BCH2026 rule sets — for three
  commitments: the empty minting baton, `FIXTURE_ANALYST` and `FIXTURE_ENTRY_LEVEL`. All three
  leave a single truthy stack element with no error, and the altstack decodes to exactly the
  fixture values, including the zero-tax, zero-allowance case:
  `3500000 / 200000 / 102160 / 5 / 23 / true / 1001` and `1600000 / 0 / 0 / 0 / 23 / true / 1002`.
- The SHA-256 printed by `05-publish-bcmr.ts` matches `shasum -a 256` on the file it wrote.
- The OP_RETURN locking bytecode it prints is byte-identical to CashScript's own
  `addOpReturnOutput(['BCMR', '0x<hash>', '<uri>'])`, and structurally identical to the worked
  example in the CHIP.
- `https://bcmr-chipnet.paytaca.com` answers, and its `/api/status/latest-block/` reports a
  chipnet height, so the chipnet indexer instance in section 6 is real.

Read from Paytaca's indexer source, not tested against a running instance:

- **Paytaca does not yet render parsable-NFT fields.** `bcmr_main/metadata.py` matches an NFT
  type key against the literal commitment hex and requires `capability='none'`
  (`# TODO: Refactor this later to support parseable NFTs`). eSahod's records are `mutable` with
  a 40-byte commitment and type keys `""`/`"01"`, so **no type match will occur**. The
  *category-level* metadata — name, description, symbol, icon — is saved on a separate code path
  and should still render, which is what T27 actually asks for. The `fields`/`parse` block is
  correct per spec and will start working in Paytaca without any change here.
- The URI and hash handling described in sections 3 and 5 comes from reading
  `bcmr_main/utils.py` and `bcmr_main/op_return.py` at `master`. That is source-reading, not
  observed behaviour, and the indexer can change.

Not checked at all:

- whether any of the icon URIs resolve. They are `esahod.example` placeholders and there are no
  actual SVG files anywhere in this repo. Until you host real icons, wallets will show a name
  with no image.
- whether a real authchain forms as described, because that depends on the `01-deploy.ts` change
  in section 2, which has not been made and has never been run.
